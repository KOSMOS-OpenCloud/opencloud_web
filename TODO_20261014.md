# 2026-10-14 — Ordner auf existierenden Ordner verschieben/kopieren: Zusammenführen statt Fehler

## Ausgangslage

Verschieben eines Ordners auf einen gleichnamigen, bereits existierenden Ordner
(cloud.xwork.cloud, WOA-Space, `__nextcloud/.../files/01 standorte` -> `01 standorte`)
endete mit HTTP 500 und einer X-Request-Id, ohne Rückfrage.

Drei Ursachen, siehe `kosmos-nuhost-deploy/BUG_posixfs_reverse_idcache.md`:

1. Server: der existierende Zielordner fehlte in der Auflistung (posixfs
   Reverse-IDCache), der Client erkannte daher keinen Konflikt und fragte nicht.
2. Server: `EEXIST` aus `os.Rename` wird nicht auf 412 gemappt -> 500.
3. **Client (dieses Repo)**: selbst bei erkanntem Konflikt bot der Transfer-Dialog
   für Ordner nur *Überspringen / Ersetzen / Beide behalten*. `MERGE` existierte nur
   für Uploads. „Ersetzen" löscht den Zielordner komplett — inklusive allem, was nur
   im Ziel liegt.

## Erledigt

### [x] Zusammenführen beim Verschieben/Kopieren von Ordnern

Gewünschtes Verhalten (Vorgabe):

- Konflikt erkennen, Nutzer wählt **Zusammenführen** oder **Ignorieren**
- Zusammenführen: alles wird übertragen, gleichnamige Dateien im Ziel werden ersetzt
- Ignorieren: nichts wird überschrieben, die kollidierenden Dateien bleiben in der Quelle
- in beiden Fällen **kein Fehler**

Umsetzung:

- `ResolveStrategy.MERGE_KEEP_EXISTING` neu (am Enum-Ende, bestehende Werte unverändert)
- `ResourceConflictModal.vue`: Prop `folderMergeOptions`. Bei Ordnerkonflikten im
  Transfer: *Überspringen / Zusammenführen, vorhandene behalten / Zusammenführen,
  vorhandene ersetzen*. Ohne das Prop unverändert (Upload, Restore).
- `conflictDialog.ts`: `resolveTransferConflict()` für Verschieben/Kopieren.
  `resolveFileExists()` bleibt unverändert, weil `upload.ts` es mit eigener
  Signatur überschreibt.
- `transfer.ts`: `collectFolderMerge()` zerlegt einen Ordner-Merge in Einzelschritte:
  - fehlt ein Eintrag im Ziel -> wird als Ganzes übertragen
  - Ordner auf beiden Seiten -> rekursiv zusammenführen
  - Datei auf beiden Seiten -> ersetzen (`overwrite`) bzw. in der Quelle lassen
  - Datei/Ordner-Typkonflikt -> in der Quelle lassen
  - je Ordner ein Abschlussschritt (`mergeFinalize`)
- Ein Ordner wird beim Transfer **nie als Ganzes ersetzt**: `REPLACE` auf einen
  Ordnerkonflikt (z.B. per „für alle anwenden" aus einem Dateikonflikt) wird zu
  `MERGE`. `MERGE`/`MERGE_KEEP_EXISTING` auf Dateikonflikte werden zu
  `REPLACE`/`SKIP`.
- Zusammenführen eines Ordners in sich selbst wird übersprungen.
- `worker.ts`: Teilschritte laufen parallel wie bisher, werden bei Erfolg aber nicht
  einzeln gemeldet (sonst landen verschachtelte Dateien in der aktuellen Ansicht).
  Danach Abschlussschritte, tiefste zuerst: beim Verschieben wird der Quellordner
  gelöscht, **wenn er leer ist**. Bleiben behaltene Einträge zurück, bleibt er
  stehen — kein Fehler. Gemeldet wird nur der vom Nutzer gewählte Ordner.
- Ergebnis-Meldung: „Zusammenführen abgeschlossen — Übertragen: X, vorhandene
  beibehalten: Y".
- `l10n`: 4 deutsche Texte ergänzt (Muster wie `67e0732398`).
- `catch` im Worker: `e.response?.headers` statt `e.response.headers` (Fehler ohne
  Response hätten die Fehlerbehandlung selbst abstürzen lassen).

Tests: 2 bestehende Specs auf `resolveTransferConflict` umgestellt (sie prüfen genau
diese Delegation), 6 neue:
- Merge mit Ersetzen / mit Behalten, Ordner wird nie als Ganzes ersetzt, kein Merge
  in sich selbst
- Worker: geleerter Quellordner wird gelöscht und nur der Ordner gemeldet;
  behaltene Einträge -> Quellordner bleibt, kein Fehler

`pnpm test:unit` für conflictHandling, pasteWorker, ResourceConflictModal: 30/30.
ESLint sauber. `vue-tsc` für web-pkg: keine Fehler in den geänderten Dateien (10
bestehende Fehler in unbeteiligten Dateien). Prettier: einzige Meldung ist die
bereits vorher zu lange `console.log`-Zeile in `worker.ts` — nicht angefasst.
