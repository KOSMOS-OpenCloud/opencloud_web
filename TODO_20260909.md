# TODO: COPY/MOVE mit falschem Zielpfad (Massenfunktion)

## Symptom

- UI-Breadcrumb: `... > Spielautomatensteuersatzung > Fassung von 2026`
- 2 Verzeichnisse ausgewählt (Versionen, Vorlagen Vergleiche Arbeitshilfen)
- "Kopieren" (Massenfunktion) → "Fehler beim Verschieben von 2 Dateien"
- COPY-Requests gehen an `Feuerwehrentschädigungssatzung/Fassung von 2016/` (falsch!)
- Ergebnis: 409 Conflict (Ziel existiert am falschen Ort)
- Request-IDs: `4a3ae3f6-fd5e-43e3-b55b-aebb18c0429e`, `4342642d-cb4b-4ab7-b1e9-eda2b5426072`
- Deployte Build: `pkg-20260907-1928` (neue Version mit Move-to-Dialog)

## Verdächtiger Code

### 1. `LocationPickerModal.vue:57-73` — kein origin/source Check

```typescript
const onLocationPick = ({ data }: MessageEvent) => {
  if (data.name !== 'opencloud-embed:select') return
  // ⚠️ Kein Check: event.source === unref(iframeRef)?.contentWindow
  // ⚠️ Kein Check: event.origin === window.location.origin
  let resources = (data.data as embedModeLocationPickMessageData)?.resources
  callbackFn(resources)
  removeModal(modal.id)
}
```

**Problem**: Jedes `postMessage` auf der Seite mit `name: 'opencloud-embed:select'`
wird akzeptiert. Wenn ein anderer iframe (z.B. Collabora, Draw.io, oder ein
zweiter EmbedModal) ein solches Message sendet, wird es fälschlich verarbeitet.

### 2. `EmbedActions.vue:94-100` — currentFolder aus iframe-Store

```typescript
const selectedFiles = computed<Resource[]>(() => {
  if (isLocationPicker.value) {
    return [unref(currentFolder)]  // ← iframe's EIGENER currentFolder
  }
  return unref(selectedResources)
})
```

**Problem**: Der iframe hat seinen eigenen Pinia-Store mit `currentFolder`.
Wenn die Navigation im iframe nicht korrekt synchronisiert ist (z.B. der
iframe noch den Startordner zeigt, aber der Benutzer bereits navigiert hat),
wird der stale `currentFolder` gesendet.

### 3. `useFileActionsCopy.ts:159` — Quelle als Startpunkt

```typescript
const parentFolderLink = getParentFolderLink(resources[0])
```

Der Picker öffnet IMMER beim SOURCE-Ordner. Der Benutzer muss manuell
navigieren. Bei tiefen Ordnern (5+ Ebenen) ist das fehleranfällig.

## Hypothesen

1. **Stale iframe State**: Der iframe-Store hat `currentFolder` noch auf
   dem Startordner (Feuerwehr/2016), obwohl der Benutzer im iframe
   navigiert hat. `emitSelect` sendet dann den stale Wert.

2. **Cross-iframe Message**: Ein anderer iframe (Collabora? Draw.io?)
   sendet ein `opencloud-embed:select` Message, das vom LocationPickerModal
   fälschlich akzeptiert wird.

3. **Routing vs. Store Divergence**: Der iframe zeigt im Breadcrumb
   "Spielautomaten/2026" (Routing), aber der Store hat noch "Feuerwehr/2016"
   (stale). `emitSelect` liest aus dem Store, nicht aus dem Routing.

## Fix-Optionen

### Fix A: origin/source Check im LocationPickerModal (sicherer)

```typescript
const onLocationPick = (event: MessageEvent) => {
  if (event.data.name !== 'opencloud-embed:select') return
  // NEU: Nur Messages von unserem iframe akzeptieren
  if (event.source !== unref(iframeRef)?.contentWindow) return
  if (event.origin !== window.location.origin) return
  // ... rest wie bisher
}
```

### Fix B: currentFolder aus Router statt Store (robuster)

In `EmbedActions.vue` statt `currentFolder` aus dem Store den Pfad aus
dem aktuellen Route lesen:

```typescript
const selectedFiles = computed<Resource[]>(() => {
  if (isLocationPicker.value) {
    // NEU: currentFolder vom Route ablesen, nicht vom Store
    const routePath = unref(router.currentRoute).params.path
    // ... currentFolder neu aufbauen
  }
  return unref(selectedResources)
})
```

### Fix C: targetFolder in onLocationPicked validieren

In `useFileActionsCopy.ts:onLocationPicked` einen Sanity-Check einbauen:
targetFolder darf nicht der Source-Ordner sein (selbst wenn der User
"Überschreiben" gewählt hat, macht eine COPY source→source keinen Sinn).

Der Zielpfad in den COPY-Requests ist NICHT der im Picker gewählte Ordner.
Die `targetFolder.path` im `TransferData` enthält einen stale/falschen Pfad.

### Aktenzeichen (fileId) wird NICHT verwendet

`getWebDavPath()` hat `path`-Vorrang vor `fileId`. Der Worker übergeht `parentFolderId`
gänzlich (`{ path: transferData.path }`). Der Ziel-Pfad kommt ausschließlich aus
`join(targetFolder.path, targetName)`.

## Root Cause (bestätigt)

**Kombination aus 3 Fehlern:**

1. **Stale iframe-Store** (Hauptursache): Der Picker-iframe hat seinen eigenen Pinia-Store.
   Wenn die Navigation im iframe nicht synchron mit dem Store ist (Routing vs. Store Divergence),
   sendet `emitSelect` den stale `currentFolder` per postMessage.

2. **Kein Message-Validierung**: `LocationPickerModal` akzeptiert `postMessage` von JEDEM
   iframe ohne `event.source`/`event.origin` Check.

3. **Copy-Handler liest aus Store statt Snapshot**: Im Gegensatz zum Move-Handler (der
   `resources` als Closure einbindet), liest der Copy-Handler aus `resourcesStore.selectedResources`
   (computed) — der zwischen Handler-Aufruf und Callback umgebaut werden kann.

## Implementierte Fixes

### Fix 1: `LocationPickerModal.vue` — origin/source Check

`isFromOwnIframe(event)` prüft `event.source === iframeRef.contentWindow` UND
`event.origin === window.location.origin`. Both `onLocationPick` und `onCancel` nutzen den Check.

### Fix 2: `EmbedActions.vue` — Route-basierter Pfad-Cross-Check

`getRoutePathFromDriveAliasAndItem()` leitet den Pfad aus der Route ab
(`driveAliasAndItem` = `driveAlias` + `path`). Wenn der Store `currentFolder.path`
davon abweicht, wird der Route-Pfad verwendet (shallow copy mit korrigiertem `path`).

### Fix 3: `useFileActionsCopy.ts` — Snapshot + Sanity-Check

- Handler bindet `resources` als Closure ein (wie Move-Handler), liest nicht mehr aus Store
- `onLocationPicked` validiert: `targetFolder.path` darf nicht der Parent eines
  Source-Ressource sein (würde zu 409/no-op führen)
